# 桌面客户端与助理架构评估报告

日期：2026-10-29。依据：[架构方案](ASSISTANT_ARCHITECTURE.md)、[阶段 0/1 任务清单](ASSISTANT_PHASE_0_1.md)、[产品方向](PRODUCT_DIRECTION.md)，以及线上代码 `d4bfcd4` 的现状核对。本文是评估与建议，不代表已做决定或已开工。

---

## 一、结论

1. **值得做桌面客户端，但它的价值在“本地工作区 + 后台执行”，不在“把网页装进一个壳”。** 对物流 B 端用户，日常大量 Excel / Word / PDF 来自业务系统导出、共享盘和本机文件夹，批量核对、汇总、按模板出报告、写回原目录，这些是网页助理结构性做不好的事。
2. **先花 2—3 周验证需求，再投入客户端。** 现在网页连上传文件都没有，还不知道用户真实的文件工作量有多大。先用低成本手段（网页上传 + 浏览器授权文件夹读写）观察 5—10 位用户实际交给 Relay 的文件任务，满足门槛再做客户端。
3. **身份独立、飞书抽离和桌面客户端可以两条线并行，不必串行等待。** 设备登录用的是 Relay 自己签发的会话，和背后是不是飞书登录无关。你的方案把客户端放在阶段 3（排在身份独立、可靠执行之后），按目前人力估算要几个月后才能见到客户端；建议拆出一条窄的客户端试点线。
4. **客户端第一版只做“固定能力”，不开放任意脚本执行。** 读取 / 搜索 / 解析 / 核对 / 生成 / 写回这几类能力用 Relay 现有的 Python 文件代码就能覆盖，不需要沙箱；任意脚本是风险和成本最大的部分（你的方案也承认 Windows 上读取隔离做不完整），放到后面。
5. **桌面壳直接选 Electron，不做 DeepSeek Harness 的 A/B 两条路径对比。** 上游是 `0.2.2-alpha` 的完整产品，为了复用它的进程/沙箱组件去 fork 整个宿主，维护成本高于收益；它的设计可以借鉴，组件不作为第一版依赖。
6. **助理间协作方向对，但它依赖“对方也在用 Relay”的网络效应，排在最后是对的。** 第一版先做“我的助理替我向同事发起委托、跟到交付”，对方不用 Relay 也能参与。

## 二、对两份文档的理解

我理解你要的是：

- **一个人一个助理（幕僚长）**：持续理解用户目标、维护背景和进度、替他推进事情，需要他决定时带着依据回来。
- **飞书只是渠道之一**：登录身份、资料来源、消息渠道、操作工具分开连接、分开授权；没有飞书也能用，以后能接别的 IM、邮箱、业务系统。
- **自己的账号与组织体系**：组织、成员、角色、外部身份绑定，支撑卖给不同企业。
- **本地 + 云端协同**：云端保存持续状态，桌面处理本地文件，电脑离线时云端继续，依赖本地的步骤等待设备上线。
- **助理之间可以协作**：围绕明确的委托请求、承接、交付、验收推进，私人对话和记忆不串。

### 写得好的地方（建议保留）

- 授权、执行、核验、目标完成四件事分开；“结果未知不盲目重试”“文件写对 ≠ 数据真实”这些原则和 Relay 现在的做法一致，是这个产品可信的根基。
- 同一业务对象只有一条写入路径；展示可以聚合，状态不复制。这正是我们最近在“同一件事跨入口、跨渠道”上踩过的坑。
- 迁移顺序（新增结构 → 幂等回填 → 兼容读取 → 分批切换 → 再清理）和回滚不抹去已发生操作，都是对的。
- 第一版暂缓全盘扫描、开放命令、桌面点击、OCR、离线大模型，范围意识很好。

### 需要补充或调整的地方

| 问题 | 说明 | 建议 |
| --- | --- | --- |
| 缺需求验证 | 两份文档都从架构出发，没有“用户每周到底有多少本地文件任务、什么类型、多大”的数据 | 加一个阶段 0′：需求观察和低成本试验（见第四节） |
| 客户端排得太晚 | 阶段 0（6 项）+ 阶段 1（11 项）+ 阶段 2 完成后才进客户端；身份独立对客户端不是硬前置 | 拆成并行的客户端试点线，共用 P0-04 的执行契约 |
| 选型成本偏高 | EX/A/B 共 9 项选型任务，其中路径 A 要 fork 上游 alpha 版完整产品 | 直接 Electron + Relay 自己的窄执行服务；Harness 只作参考 |
| 平台优先级未定 | 印尼企业办公以 Windows 为主 | 第一版 Windows 优先，Mac 跟进；Windows 代码签名证书提前采购 |
| 目标客户未定 | “自建账号体系”的紧迫程度取决于是否面向 J&T 以外的企业；若近期只服务内部且全员有飞书，身份独立可以后置 | 先决定商业化时间表，再定阶段 1 的优先级 |
| 流程偏重 | 每项任务都要证据模板、负责人、验收记录；对小团队会拖慢节奏 | 保留停止条件和关键验收，日常任务用 PR + 测试作证据即可 |

## 三、现状核对（代码 `d4bfcd4`）

| 事实 | 对决策的影响 |
| --- | --- |
| 网页**没有文件上传**；文件只能来自邮件附件和飞书云文档 | 本地文件需求目前完全没有被满足，也没有被测量过 |
| 文件解析和生成全部是 Python（openpyxl、python-docx、python-pptx、pypdf；`sources/files.py`、`outputs.py`），生成后会重新打开逐项核对 | 本地执行服务用 Python 可以直接复用这些代码和核对逻辑，这是选型的关键因素 |
| 后端 60 个文件引用飞书；66 个工具大多是飞书能力；`users.feishu_open_id` 是必填且唯一 | 飞书抽离是大工程，应和客户端分开推进，不要互相等待 |
| 长期任务（Mission）已有计划、等待、唤醒、三层证据；文件生成已有后台任务、重试和重启接续 | 云端“离线继续”的基础已有；缺的是“设备”这一类执行者和对应的认领/心跳 |
| worker 已改为用户并行、按用户加锁、聊天提取独立循环 | 本地执行的回执回到云端时，可以沿用按用户加锁的写入方式 |
| 前端是 React + Vite 单页，没有依赖浏览器以外的能力 | 可以原样装进 Electron，增加少量桌面专用入口 |

## 四、问题 1：是否值得开发桌面 App

### 哪些事必须在本地做，哪些网页也能做

| 需求 | 网页能否做好 | 说明 |
| --- | --- | --- |
| 偶尔处理一两个文件 | 能 | 加上传 / 拖拽即可，云端已有解析和生成 |
| 处理一个文件夹里的几十上百份文件 | 部分能 | Chrome/Edge 的文件夹授权（File System Access API）可以读写用户选定的目录，但标签页关闭就停，不能后台 |
| 按目录结构写回成果、覆盖前核对版本 | 部分能 | 同上，只在标签页打开时 |
| 文件很大或不愿意上传（合同、薪资、客户数据） | 不能 | 需要在本机解析，只把必要片段送去模型 |
| 盯着一个文件夹，新文件到了自动处理（例如每天业务系统导出的报表） | 不能 | 需要常驻进程 |
| 电脑休眠/重启后接着做、和云端任务衔接 | 不能 | 需要设备身份、认领和心跳 |
| 打开 / 定位本地成果、系统通知、托盘常驻、拖拽 | 体验差 | 桌面原生交互 |
| 操作本机其他软件（Excel 宏、本地 ERP 客户端） | 不能 | 属于桌面操作，风险最高，后置 |

**判断**：只要用户的文件工作是“经常、成批、敏感、需要盯着”的，桌面就是必需的。物流运营、财务、客服管理岗位大概率是这样，但需要用数据确认，而不是假设。

### 先验证需求（2—3 周，几乎不影响主线）

1. **网页加文件上传和拖拽**（单文件 + 多文件，复用现有解析和生成）。这本身就是 Relay 缺的基础能力，不浪费。
2. **Chrome/Edge 上加“授权一个文件夹”**（File System Access API）：读取、搜索、生成成果写回同目录。验证“成批处理本地目录”的真实使用频率。
3. **观察 5—10 位用户**：他们一周有哪些文件任务、多大、多少份、是否敏感、是否周期性。

**进入客户端开发的门槛（建议）**：试点用户里，每周至少有一半的人交给 Relay 文件任务；其中成批（≥10 份）、周期性或因敏感拒绝上传的占比显著（例如 ≥30%）；或出现明确的“要后台盯文件夹 / 要写回共享盘”的需求。达不到就先把网页文件能力做好，客户端推迟。

### 成本与风险

- **持续成本**：Windows / Mac 两套安装包、代码签名（Windows 证书、Apple 开发者账号与公证）、自动更新、版本兼容、用户机器上的各种环境问题和支持工作。这是长期负担，不是一次性开发。
- **安全责任**：本地执行意味着 Relay 能读写用户电脑上的文件，授权边界、撤权、审计必须做到位，出事影响比网页大。
- **收益**：打开“处理本地文档”这一整类高频工作，是从“提醒助理”走向“能干活的幕僚长”的关键一步；同时是 B 端产品的差异点。

## 五、问题 2：如果做，怎么做

### 5.1 推进方式：三条线

```
线 A（身份与渠道）：阶段 0 盘点/决策 → 阶段 1 独立身份、飞书适配、连接管理
线 B（本地工作区）：需求验证 → 设备与执行契约 → 客户端 MVP → 试点 → 扩展
线 C（可靠执行）  ：运行记录、认领、心跳、结果未知、待发送通知（线 B 的设备执行依赖其中最小的一部分）
```

- 线 B 只依赖线 C 的最小子集（执行记录 + 认领 + 心跳），不依赖线 A 完成。设备登录使用 Relay 会话，背后现在是飞书登录，以后换成独立身份时设备不用重新设计。
- 三条线共用阶段 0 的 P0-04 契约：执行请求/结果、授权版本、证据三层。这是唯一必须先定下来的东西。

### 5.2 技术选型

| 部分 | 建议 | 理由 |
| --- | --- | --- |
| 桌面壳 | **Electron** | 现有 React 界面原样复用；Windows/Mac 成熟；electron-updater 自动更新、托盘、通知、文件对话框都现成；团队技术栈是 TS + Python，不引入 Rust（Tauri 包更小，但团队成本更高） |
| 本地执行服务 | **Python 进程（随应用打包，PyInstaller 或嵌入式 Python）** | 直接复用 `sources/files.py`、`outputs.py` 的解析、生成、逐项核对；和后端同一套代码和测试 |
| 壳与执行服务通信 | 本机回环 + 每次启动随机令牌；界面只能调用白名单接口 | 网页内容、文件预览不能调用执行接口（方案 7.3 的要求） |
| 设备与云端通信 | 设备主动发起的 WebSocket（不在用户电脑开端口），云端下发执行请求，设备回传进度、回执、成果和核验 | 防火墙友好；断线重连后按执行 ID 核对，不重复执行 |
| 模型调用 | 仍经过云端 | 密钥不下发到设备；只把必要片段发给模型，片段和日志受同一数据边界约束 |
| DeepSeek Harness | 参考它的进程管理、取消、输出限额设计，第一版不依赖其包 | 上游是 alpha 版完整产品，剥离成本和跟随升级成本高；Relay 第一版不需要通用 shell |

### 5.3 第一版（MVP）范围

**做**：
- 登录同一 Relay 账号、配对一台主要设备、可撤销。
- 授权目录：读、写分开授权；执行时检查路径、软链接、版本。
- 本地文件：文本型 PDF、DOCX、XLSX、CSV、TXT 的解析、搜索、带页码/单元格定位的引用。
- 任务：核对多份文件、汇总、按模板生成 Excel/Word/PPT，默认新建文件，覆盖需确认且版本一致；生成后重新打开核对（沿用现有逻辑），并注明数据来源。
- 接续：设备离线时，依赖本地的步骤显示“等设备上线”，云端步骤继续；重启后核对已执行的写入，不重复。
- 桌面交互：拖拽、打开成果所在位置、托盘、完成通知；对话、待处理、会议、邮件与网页同一个工作台。

**不做（第一版）**：任意脚本/命令、全盘扫描、文件夹自动监听（第二版首选）、操作其他软件、扫描件 OCR、离线模型、多设备同时执行。

### 5.4 关键设计点

1. **设备是一种执行者，不是另一个助理。** 任务状态仍只在云端 Mission / 执行记录里；设备只回传执行结果和证据，不能直接关闭目标。
2. **三层授权同时满足才执行**：任务授权（用户交代了什么）、目录授权（选了哪些文件夹、读还是写）、设备授权（这台设备是否仍有效）。撤权后未执行的步骤在执行前被拦下。
3. **执行可核对**：每一步有执行 ID、输入文件版本（大小 + 修改时间 + 哈希）、输出文件版本；重发同一 ID 返回原回执；结果未知时先核对目标文件，不重做。
4. **数据不出设备的边界写清楚**：原文件、完整索引、解析缓存留本地；送到模型的片段、成果交付给他人的副本需要可见、可审计。
5. **统计只收数字**：执行次数、耗时、失败类型，不收文件正文和完整路径。

### 5.5 阶段与粗略工作量

以下按 1—2 名全职开发 + AI 辅助估算，只作排期参考，实际以阶段 0 盘点为准：

| 阶段 | 内容 | 粗略周期 | 出口 |
| --- | --- | --- | --- |
| B0 需求验证 | 网页上传/拖拽、浏览器文件夹授权、用户观察 | 2—3 周 | 达到上面的门槛才继续 |
| B1 契约与设备 | 执行请求/结果契约、设备配对与撤销、执行记录/认领/心跳最小版、WebSocket 通道 | 3—4 周 | 云端能向一台测试设备下发、取消、重发一个执行并拿回回执 |
| B2 客户端 MVP | Electron 壳、Python 执行服务打包、授权目录、解析/生成/核对、离线接续 | 5—7 周 | Windows 干净机器上安装即用；授权拒绝、撤权、文件被改、断网、休眠场景通过 |
| B3 试点 | 5—10 位用户、Windows 优先、签名与自动更新、诊断日志 | 4 周观察 | 无越权、无误写、无重复副作用；文件任务完成率和节省时间可量化 |
| B4 扩展 | 文件夹监听、Mac 版、受控脚本（满足隔离才开放）、协作中的文件交付 | 按试点结果 | — |

线 A（阶段 0/1）按你的任务清单推进，估计 8—12 周；和线 B 并行时，两者共用阶段 0 的契约产出。

### 5.6 主要风险与对策

| 风险 | 对策 |
| --- | --- |
| Windows 环境千差万别（权限、杀毒软件、代理、路径编码） | 第一批试点机器覆盖常见公司电脑；内置诊断；Python 运行时随包分发，不依赖用户环境 |
| 签名与更新出问题导致无法升级 | B1 就申请证书、搭更新源；演练一次失败回退 |
| 本地写入误伤用户文件 | 默认只新建；覆盖前版本核对 + 确认；保留恢复信息；取消不伪称回滚 |
| 两份状态（设备本地 vs 云端）不一致 | 状态权威只在云端；设备只存执行缓存，重连后按执行 ID 对账 |
| 范围蔓延到“通用电脑助手” | MVP 坚持固定能力清单；任意脚本和桌面操作单独立项并通过隔离验收后才开放 |
| 维护负担拖慢主线 | 一个人专门负责客户端分发和支持；先 Windows 单平台 |

## 六、对飞书抽离与自建账号体系的建议

- **方向同意**：飞书是渠道、资料来源、操作工具和外部身份之一，Relay 自己的用户、组织、成员、连接是根。
- **先回答一个商业问题**：多久之后要服务 J&T 以外、或不用飞书的组织？如果是半年以上，阶段 1 可以先只做“内部抽离”（能力查询、连接与登录分开、去掉 `feishu_open_id` 必填），正式非飞书登录（OIDC）等有客户时再接；如果近期就要，按你的阶段 1 全量推进。
- **抽离的顺序**：先做能力查询和执行上下文（P1-04）、连接与登录分开（P1-03），这两项让后续所有新渠道（包括桌面设备）都有地方挂；数据同步、通知、业务系统入口逐个迁移。
- **保持现有行为不退化**：最近两周修好的“同一件事跨渠道”“提醒去重”“一件事一张卡片”等，都要进阶段 0 的回归场景。

## 七、对助理间协作的建议

- 第一版建议做成“**我的助理替我发起委托并跟到交付**”：对方用 Relay 时由对方助理承接、拆解和回传；对方不用 Relay 时通过飞书/邮件参与，状态由我的助理根据回复判断（现有能力已经能做大半）。
- 不做助理之间的自由对话；每一步都落在委托对象上（请求、接受/协商、提交、验收），私人对话和记忆不共享。
- 协作的价值随使用人数增长，适合在组织内用户密度够高（例如一个部门全员在用）后再推。

## 八、需要你决定的事

1. 商业化时间表：是否、何时服务 J&T 以外或不用飞书的组织（决定线 A 的优先级和身份方案）。
