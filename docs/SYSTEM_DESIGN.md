# Relay 系统设计：用户体系、个人助理、连接器、本地项目

> 2026-10-30。用来对齐接下来的工程方向。原则：从用户场景和工程流程出发，定义每一部分的**输入、输出、状态、权限、失败方式**，
> 用代码和契约保证行为，不靠在提示词里“设想”模型会怎么做。

## 〇、对需求描述的几处修正与补充

1. **“不要在系统里增加提示词来设想”——方向对，但不能做到零提示词。**
   对话模型必须有一份说明，告诉它有哪些工具。要区分的是：
   - 应该用代码保证的：工具的前置条件、参数校验、权限、状态流转、写入前确认、写入后回读核对、重试和幂等。
     这些现在有一部分写在系统提示词里，靠模型“自觉”，要改成工具契约。
     例如“问抄送我的审批要用 `category=cc`，不能显示批准按钮”，应该由工具的输入枚举和返回结构保证，而不是写一条提示。
   - 只能由模型做的判断：例如“这封邮件要不要他处理、他要做什么”“这段群聊里谁答应了什么”。
     这类不靠加规则文字改进，而是定义**输入、输出结构和评测集**，用真实样本的准确率来改进。
   - 现状：系统提示词约 40 条行为规则；后台有 16 处模型调用（邮件分级 3、事项推进 5、会议 3、群聊 2、提醒档位 1、起草 1、任务验收 1）。
     第三节、第六节给出迁移办法。

2. **“参考 Claude 的最佳实现”需要具体化**，否则容易各自理解。可借鉴的是这几件事：
   - **项目（Projects）**：一个工作对象 = 一组资料 + 一份说明 + 产出位置。对应到 Relay：一个授权文件夹就是一个项目。
   - **技能（Skills）**：确定性的步骤写成脚本，按需加载，可以单独测试；说明只描述“什么时候用、输入输出是什么”。
     注意技能里也有说明文字，它和“在系统里设想”的区别在于：可测、按需、配套脚本，而不是全局规则。
   - **连接器标准（MCP）**：每个外部系统暴露 tools / resources，输入输出用 JSON Schema 描述。业务系统接入建议直接采用。
   - **权限模型**：读、写分开授权；写入前给出差异预览；默认新建而不覆盖。
   - **产出可核对**：生成的文件重新打开核对，写明数据来源。
   - Relay 已经做了其中几项（授权文件夹、写入只新建、生成后核对），缺的是“项目说明”、“技能”和“连接器标准”。

3. **团队组织对个人助理的作用要说清楚**，否则会又变成派任务的系统。组织信息在 Relay 里只用来：
   - 判断重要程度（上级、直属团队的事优先；现在依赖飞书的上级链）；
   - 决定可见范围（管理员能看什么统计，团队负责人能看什么汇总）；
   - 给助理背景（同事是谁、在哪个部门、负责什么）。
   不用于给人派任务——派任务用飞书任务。

4. **“飞书只是一个渠道”和“现在只接飞书”不矛盾**：架构上飞书是连接器中的一个，按统一契约实现；实施上这一阶段只实现飞书，
   其他系统按需再接。

5. **业务系统接入有两个方向，现在只有一个**：
   - 已有：业务系统把事件推给 Relay（TMS 异常、审批结果……），落成成员的待处理。
   - 没有：助理去业务系统**查**数据（货量、库存、时效）。这是另一个方向，需要连接器契约（第四节）。

6. **已经做了、但不在本阶段重点里的**：标准邮箱和日历订阅（IMAP / ICS）、表单式协作委托。保持现状，不再扩展。

## 一、个人助理的定位：输入与输出

| | 定义 |
|---|---|
| 服务对象 | 一位成员本人（一个工作区里的一个 User）。所有数据、记忆、事项都挂在他名下，别人看不到 |
| 输入 | ① 他接入的数据源产生的信号（邮件、日程、审批、消息、业务事件……）② 他在对话里说的话 ③ 他授权的本地文件夹 |
| 输出 | ① 待处理事项（要他做的 / 在等别人的），带来源证据 ② 在合适的时间告诉他（按他的提醒规则）③ 准备好的成果（草稿、文件、会前材料），写入前要他确认 ④ 对话里的回答 |
| 不做 | 替他承诺；替别人做决定；派任务给别人；读别人的私人数据 |
| 判断的依据 | 只用有来源的事实（信号、文件、记忆），每条事项、每个结论都能追溯到来源 |

每一种输出都要能回答三个问题：**依据是什么（来源）、现在是什么状态、他能做什么操作**。现有的事项、卡片、证据链已经按这个做，后续新功能照此验收。

## 二、用户体系与团队组织

### 已有

| 对象 | 说明 |
|---|---|
| 账号 Account | 登录身份（邮箱 + 密码，或飞书登录） |
| 工作区 Tenant | 一家公司。不跨公司 |
| 成员 User | 账号在某个工作区里的身份；角色：所有者 / 管理员 / 成员；可停用 |
| 邀请 | 链接邀请，7 天，一次性 |
| 接入 | 每个工作区自己的飞书应用配置（加密保存） |

### 要做

| 对象 | 字段 | 来源 | 用途 |
|---|---|---|---|
| 部门 Department | 名称、上级部门、负责人 | 管理员维护；接了飞书时从飞书通讯录同步（同步来的标记来源，不覆盖手工改的） | 组织架构、可见范围 |
| 成员资料 | 部门、上级（manager）、岗位、职责、负责的客户 / 线路 / 项目 | 同上 + 本人补充 | 判断重要程度、助理背景 |
| 团队 Team | 名称、成员、负责人（可跨部门，例如“Medan 项目组”） | 管理员或负责人创建 | 团队负责人看团队汇总 |
| 可见范围 | 本人 / 团队负责人（团队成员的事项数量和逾期，不含内容）/ 管理员（工作区统计） | 规则写在代码里 | 防止助理变成监控工具 |

**验收**：没接飞书的公司能完整建立组织架构；接了飞书的公司一键同步，之后飞书里改了能同步过来、手工改的不被覆盖；
提醒分级里“上级的事优先”改为读 Relay 自己的上下级关系，飞书上级链只作为同步来源。

## 三、连接器：统一契约

每个外部系统（飞书、以后的业务系统）都按同一个契约描述，代码里有一份机器可读的清单，文档和测试由它生成。

### 3.1 连接器 Connector

| 字段 | 说明 |
|---|---|
| 身份与授权 | 工作区级（应用凭证，管理员配置）/ 成员级（个人授权，例如飞书用户令牌）；需要哪些权限范围 |
| 健康状态 | 未配置 / 正常 / 授权过期 / 权限不足 / 服务不可用；每种状态给成员和管理员的提示不同 |
| 数据源 Sources | 见 3.2 |
| 工具 Tools | 见 3.3 |
| 事件 Events | 外部系统推来的事件（飞书消息、卡片回调、业务系统事件）：校验方式、去重键、落到哪里 |

### 3.2 数据源 Source（只读，后台同步）

| 字段 | 说明 |
|---|---|
| 输出 | 统一写成 Signal：`source / kind / external_id / title / body / payload / occurred_at`，payload 的结构按 kind 定义并校验 |
| 同步方式 | 轮询（间隔）或事件推送；增量游标；首次同步的回看范围 |
| 失败分类 | 未开通（隔一段时间再试，不算故障）/ 授权问题（提醒重新授权，24 小时一次）/ 暂时失败（下轮重试） |
| 去重 | `user + source + external_id` 唯一 |

### 3.3 工具 Tool（助理调用）

| 字段 | 说明 |
|---|---|
| 输入 | JSON Schema（已有） |
| 输出 | 结构化结果 + 给模型看的文字（现在只有文字，要补结构） |
| 副作用等级 | `read`（只读）/ `prepare`（只准备，等本人确认）/ `write`（执行写入，只能由确认动作触发） |
| 前置条件 | 由代码检查，不满足时返回明确的错误码（例如“没有授权 / 应用没开通 / 他对文件没有编辑权限 / 不支持”） |
| 核对 | 写入后的回读核对方式；核对不一致如实返回 |
| 幂等 | 写入的幂等键；结果未知时先核对，不重做 |

### 3.4 把系统提示词里的规则迁到契约（示例）

| 现在写在提示词里 | 改成 |
|---|---|
| 问抄送的审批用 `category=cc`，不能显示批准按钮 | 工具输入是枚举，返回结构里只有 `pending` 才带可批准标记，前端按标记渲染 |
| 写不了时不要笼统说“没有权限” | 工具返回错误码（app_scope / file_permission / unsupported），前端和模型都按错误码显示 |
| 同一类查找换关键词最多三次 | 工具层按对话轮次计数，超过次数返回“已查过：……” |
| 准备不等于执行，须等待确认 | 已经由 `prepare` 等级保证；提示词里这条可以删 |
| 文件核对只证明文件写对了 | 返回结构里分开 `file_check` 和 `data_sources`，界面分开显示 |

目标：系统提示词只剩“你是谁、为谁工作、有哪些工具（由清单生成）、上下文块的含义”，行为规则都在契约里。

## 五、业务系统接入

| 方向 | 状态 | 契约 |
|---|---|---|
| 事件推入（业务系统 → Relay） | 已有：专属地址 + 签名 + 去重 + 收件人解析，只投递本工作区 | 保持；事件结构按 kind 定义 schema |
| 查询（助理 → 业务系统） | 没有 | 建议采用 MCP（或 OpenAPI 描述）：工作区管理员登记连接器地址和凭证；Relay 读取它声明的工具和 schema；默认只读；每次调用记审计（谁、查了什么、返回多少） |
| 写入（助理 → 业务系统） | 不做 | 以后需要时按 `prepare → 确认 → write → 回读` 同样的流程 |

**验收**：接一个业务系统不改 Relay 代码，只做配置；助理能看到它声明的工具；成员只能用他所在工作区登记的系统。

## 六、本地文件与项目（Mac 客户端）

### 已有
授权文件夹（读写分开）、列 / 读 / 存新文件、路径与软链接检查、写入只新建并回读核对、设备配对与撤销、离线时明确说明。

### 要做（参考 Claude 的项目与技能）

| 能力 | 定义 |
|---|---|
| 项目 | 一个授权文件夹 = 一个项目。可选一份说明文件（例如 `RELAY.md`：这个项目是什么、数据在哪些文件、产出放哪），由本人写，助理读，不由系统设想 |
| 读取 | 本机解析（Python 执行服务，复用现有解析代码），只把需要的片段送出；引用带定位（文件 + 工作表 + 单元格 / 页码） |
| 加工 | 固定的技能，每个技能定义输入（哪些文件、什么参数）、输出（新文件 + 核对报告）、核对方式。第一批：多份 Excel 核对差异、按模板汇总、从多份文件生成周报 |
| 修改已有文件 | 先生成差异预览，本人确认；写入前核对文件版本（大小 + 修改时间 + 哈希）没变；默认另存，覆盖要单独确认 |
| 不做 | 任意脚本和命令、全盘扫描、操作其他软件 |

---

### 补充约束（2026-10-30 确认）

- **配置在服务端**：连接器凭证、工作区配置、技能定义、权限规则都放在服务端；客户端只保存登录所需的设备令牌（系统钥匙串加密）。
  客户端里的东西都可能被拆包查看，不能当作秘密或权威。
- **哪些放本地**（以后设计，参考 Claude）：项目产出的文件、项目相关的技能、对话存储的分工（云端与本地各存什么）。
- **客户端渲染**（以后）：按用户交互需要生成 html / md / pdf / word / excel，在客户端里打开渲染。
- **前期保持专注**：先把飞书这套理清楚、组织架构和注册登录创建团队做完，再做复杂设计。

## 八、需要确认

1. 第〇节的几处理解是否正确，尤其是“团队组织只用于重要程度、可见范围和背景，不用于派任务”。
2. 阶段顺序：建议 1 → 2 → 3 → 4 → 5；本地项目（4）也可以和 2 并行。
3. 业务系统查询是否采用 MCP 作为标准（第五节）。
