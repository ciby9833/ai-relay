AI 不是许愿池：业务系统里的 AI 是怎么干活的

客服问 AI：“SG123456 到哪了？”它答得很干脆：“已到达雅加达中转仓，预计明天派送。”实际上这票货卡在 GW 中转环节，分拣出了异常，已经两天没有新轨迹。AI 没出故障，它只是从头到尾没看到这票货的任何数据。

2026 年 10 月 23 日 · Relay 团队

“把资料给 AI，它就能解决”，这是很多人对 AI 的第一印象。真把 AI 放进业务系统，就会发现它的表现几乎完全取决于周围的设计：它看到了什么，能查什么，能做什么，什么时候停下来。弄懂它怎么工作，这些设计就不难想清楚。

原理篇

一、它其实在“接话”

现在说的 AI，大多指大语言模型。训练时它读了海量文字，反复做同一道题：遮住后面的内容，猜下一个词是什么。猜得足够多以后，它学会了语法、常识和一些推理的套路。

用的时候也一样。它把你给的文字读一遍，算出下一个词每个候选的可能性，挑一个写上，再接着算下一个。一段回答就是这样一个词一个词“接”出来的。

这个机制解释了 AI 的几个特点：

  • 它追求的是“像”，不是“对”。候选词的可能性来自它读过的文字，与事实是否正确没有直接关系。
  • 同一个问题，两次回答可能不一样。挑词时有一定随机性，排第二的词偶尔也会被选中。
  • 它按“词块”计算和计费。模型把文字切成小块处理，叫 token，中文大致一个字左右一块。输入和输出越长，越慢也越贵。

二、它只看得到这一页纸

每次调用模型，它能读到的全部内容叫“上下文”：给它的工作说明、附上的资料、之前的对话、用户的问题。上下文之外的东西，对它来说不存在。

聊天工具看起来记得前面聊过什么，是因为程序每次都把前面的对话重新发了一遍。模型本身不记事。上下文的长度也有上限，塞得太多，它反而容易忽略中间的内容。

开头那个答错的例子就发生在这里。上下文里只有一个问题，它只能按“这类问题通常怎么回答”往下接，接出来的话很像真的。这种情况叫“幻觉”。

所以在业务系统里用 AI，要解决的第一件事是：每次调用时，往上下文里放什么。接下来三节讲的知识库、工具和智能体，都是围绕这件事的办法。

三、让它知道公司的事：知识库

公司的规则、流程、口径有成百上千条，不可能每次都全部塞进上下文。常用的做法是先检索、再回答：用户提问后，程序先去知识库里找出最相关的几条，和问题一起交给模型。这种做法叫检索增强生成，英文缩写 RAG。好比开卷考试，模型不用背整本书，只要每次先翻到对的那一页。

“找相关”靠的是向量。程序事先把每条知识转成一串数字，意思越接近的两段话，数字越接近。所以客户问“货两天没动了是怎么回事”，即使知识库里写的是“中转站超过 48 小时无新轨迹，按运输超时处理”，几乎没有相同的字，也能匹配上。

知识库的效果主要取决于知识本身写得好不好。一条好用的知识，只讲一个问题，写清楚四样东西：遇到的是什么情况，怎么处理，去哪个系统查，结论是什么。条件和数字写具体。一份几十页的制度文件整个放进去，效果通常不如几十条这样写好的短条目。

四、让它动手：工具调用

知识库解决的是规则，实时数据要靠工具。做法是告诉模型：“你可以用 query_waybill(运单号) 查轨迹”，并写清楚这个工具是做什么的。模型读完问题，自己判断要不要查、查哪个单号。

要注意的是，模型自己不会执行任何操作。它只是输出一句结构化的请求：“我要调用 query_waybill，参数是 SG123456”。真正去查系统的是我们的程序。所以哪些系统能查、哪些字段能看、哪些操作要人确认，控制权都在程序这一边，也就是在产品设计这一边。

五、让它自己推进：智能体

上面的例子里，模型查一次就够了。很多实际问题要查好几次：查了轨迹发现货在 GW 停了两天，要再查异常记录；发现是面单破损，可能还要查 GW 的处理进度。让模型在一个循环里自己决定下一步、调用工具、看结果、再决定下一步，直到办完，这样的程序叫智能体（Agent）。

智能体能处理更复杂的事，也更难控制：步骤越多，花的时间和费用越多，中途走偏的机会也越多。所以有三样东西不能少：

  • 步数上限。到了上限还没办完，就停下来交给人。
  • 操作分级。查询可以让它自己做；改单、发消息这类会改变业务状态的操作，只让它准备好，等人确认。
  • 办完的标准。事先写清楚“什么算办完”，最后对照着检查，而不是它自己说完成就算完成。

还有一个经验：能用固定流程解决的，就别让它自由发挥。先用程序写死“查轨迹，再查异常记录，最后让 AI 总结”，跑稳了再考虑让它自己决定顺序。

产品篇

六、产品上怎么定义一个 AI 功能

前面五节可以归成四个台阶。定义一个 AI 功能，先想清楚它要站在哪一级。级别越高，能做的事越多，要设计和控制的东西也越多。

台阶比上一级多了什么典型用法要防的问题
1. 只靠说明写好的工作说明和格式要求改写邮件、翻译、总结会议记录涉及公司的事会编
2. 加知识库能查公司的规则和资料内部流程问答、客服口径资料过期或写得含糊就答错
3. 加工具能查实时数据，能提出操作运单查询、开单信息识别改数据的操作必须人确认
4. 智能体自己决定下一步，多轮推进跟进超时件直到恢复运输费用、走偏、何时算办完

先找麻烦，再找 AI

“我们也要做个 AI”很难落地。“客服每天花两小时在三个系统之间查运单”就能直接拿来设计。判断一个场景值不值得用 AI，可以问三个问题：

  1. 每天要做很多次吗？一个月做两次的事，做 AI 不划算。
  2. 输入是杂乱的文字吗？规则清楚、数据规整的事，写普通程序更快也更稳。AI 的长处在处理人说的话、写的字。
  3. 做错了代价大吗？代价小的可以全自动；代价大的让 AI 先出草稿，人来确认。
物流里的常见场景台阶AI 负责的部分建议从哪里做起
运单查询3把几个系统的结果合成一句结论程序按固定顺序查，AI 只做最后的总结
客服回复2–3理解问题，结合规则和运单起草回复先做“AI 起草、客服确认后发送”
开单信息识别3从客户消息里提取开单字段填进表单，拿不准的字段标出来让人补
用自然语言查数据3把问题转成查询语句，解释结果先只支持一类问题，比如每日单量
内部问答2回答同事关于流程的问题从过去的聊天记录里整理问答，审核后入库
异常件跟进4多轮查询、联系、等回复，直到解决前三级跑稳以后再做

四个必须回答的问题

问题产品要给出什么以运单查询为例
它要知道什么工作说明，以及要用到的业务规则时效规则、常见异常的处理办法、回复客户的口径
它能动用什么能查哪些系统、哪些字段；能不能改数据能查轨迹和异常记录；不能改单
什么时候交给人哪些情况它不该自己处理，交给谁查不到单号、客户要赔偿、涉及改地址，转客服
怎样算做对一组真实问题和标准答案，作为验收依据30 个历史咨询，每个写清回答必须包含的要点

最后一个问题最容易被跳过。普通功能按步骤点一遍就能验收，AI 功能不行：改了一句说明，这个问题答对了，另一个问题可能就答错了。所以要有一组固定的测试问题，每次调整后完整跑一遍，看答对的比例有没有下降。这组问题由最懂业务的人来写。

放进产品时的几个做法

  • 放在用户已经在用的页面里。在运单详情页加一个“帮我看看”按钮，比另开一个聊天窗口更容易被用起来。面对空白的对话框，很多人不知道该问什么。
  • 让用户看到依据。结论旁边写明来自哪个系统、哪条规则，用户才敢用。
  • 随时可以转人工。AI 拿不准时主动转，用户不满意时也能一键转。
  • 只给完成任务需要的数据。证件号、密码、银行卡号不要发给模型。
  • 记录每一次使用。问了什么、答了什么、用户觉得有没有用。这些记录就是下一版的测试问题和知识库素材。

七、案例：Relay 是怎么定位、怎么起步的

Relay 是我们公司内部的 AI 助理，接在飞书的邮箱、日历、审批、群聊和业务系统上，属于上面的第 4 级。它从一个模糊的想法变成现在这样，中间做了几次关键的判断。

从“什么都能做”收窄到一件事

最初的设想很宽：一个什么都能问的个人助手，能记住你，能回答问题，能替你办事，能定时提醒。这样的描述适合宣传，拿来做设计却无从下手，不知道先做什么，也不知道怎样算做好了。

后来我们换了个问法：同事每天在哪件事上花了最多不该花的时间？答案很集中。事情散在邮件、审批和群消息里，要自己整理哪些要回、哪些在等别人，等别人的事还得记着去催。

给谁：每天被邮件、审批、群消息追着跑的同事。
替他做什么：把消息整理成一件件事，先起草好回复，把要来回追的事跟到办完。
不做什么：不替他对外拍板。发邮件、回会议邀请都先准备好，等他点确认。

第三句和前两句一样重要，它直接决定了很多设计：确认按钮只认点击者本人；邮件和文档里的内容只当资料看，就算里面写着要求，对外操作也仍然要他确认；长期任务里哪些操作可以自动做，只能由用户在界面上勾选，模型不能给自己授权。

第一版上线，数据给了当头一棒

第一版的流程很直接：消息进来，模型判断是不是要处理的事，是就建成事项推给用户。演示效果很好。上线后我们看了早期连续三天的数据：有的同事每天收到二十多条实时推送，三天新建的约 400 个事项里，约 390 个还没关闭。识别得越多，用户反而越忙，只是把邮件和群消息换个地方又说了一遍。

第二步改的不是模型，是规则：什么事值得马上打断人。

改版的细节写在《从消息提醒到可靠执行》里；Relay 现在一天里怎么用，可以看《邮件、审批、群消息，每一件事都有人跟进》里的演示视频。回头看，对做 AI 产品最有用的几条是：

  1. 定位里要写“不做什么”。AI 能做的事太多，边界不写清楚，风险和范围都会失控。
  2. 演示效果好，不代表有用。上线后看用户实际怎么处理它给的结果：打开了没有，采纳了没有，有没有被打扰。
  3. 最大的改进往往不在模型。Relay 上线后的几轮改进，大多是在改规则、改流程、补数据，而不是换模型。

八、AI 功能的方案怎么写

普通功能的方案描述页面和流程。AI 功能的方案还要写清楚：它知道什么，能做什么，状态怎么流转，什么时候停下来。下面这个结构可以直接套用，每一项附上“运单异常助手”的写法作为参考。

1. 背景和目标
现在的麻烦是什么，用数字说明；做完以后看哪个数字变化。例：运输超时和中转异常每天约 40 票，客服要在 3 个系统间查询再写回复，平均 6 分钟一票。目标：降到 2 分钟以内。
2. 用户和场景
谁在什么时候用，从哪个页面进入。例：客服在异常件列表里点“帮我处理”。
3. AI 负责的部分和台阶
一句话写清它做什么、不做什么，属于第几级。例：第 3 级。汇总轨迹和异常记录，起草给客户的回复；不直接发送，不改运单。
4. 流程和状态
列出每个状态、进入和离开的条件，以及每一步由谁完成。画出来比写出来清楚，见下图。
5. 资料和知识库
用到哪些规则和口径，由谁维护，多久更新。例：中转异常处理办法 12 条，由客服主管每月复核。
6. 系统接口和权限
每个系统查什么、哪些字段；改数据的操作单独列出，写明谁来确认。例：查轨迹、查异常记录，只读。
7. 交给人的规则
哪些情况必须转人工，转给谁，界面上怎么显示。例：查不到单号、客户要求赔偿、同一票货第二次超时。
8. 验收样例和上线标准
至少 30 个真实案例，每个写出回复必须包含的要点和不能出现的内容。上线标准写成数字。例：30 票里至少 27 票的草稿客服不改或只改措辞。
9. 上线后看的指标
使用次数、草稿被直接采用的比例、转人工比例、平均处理时长、用户反馈“没用”的记录。
10. 风险和兜底
模型服务不可用、查询超时、回答明显出错时怎么办。例：任何一步失败都退回到原来的人工流程，页面提示原因。
11. 分期计划
先做哪一级，满足什么条件再进下一级。例：一期只起草回复；采用率连续一个月超过 80% 后，二期再考虑自动跟进 GW 的处理进度。

第 4 项最值得多花时间。AI 功能出问题，多半出在状态的边界上：什么时候算处理完，谁有权推进到下一步，失败了退回哪里。

九、写方案之前，先花半天验证

请开发排期之前，自己就能判断这个场景值不值得做：

  1. 写一页工作说明。用对新同事交代工作的口气：你是谁，要做什么，参考哪些规则，遇到什么情况转给人，回答用什么格式、多长。
  2. 准备 20 个真实问题。从历史聊天、工单里挑，去掉客户的敏感信息。多挑一些难的、说得含糊的、中英印尼语混着写的。
  3. 在模型的调试界面里逐个试。把工作说明放进“系统指令”，相关规则贴在问题前面，查询结果先手工从系统里复制过去。调试界面的权限可以请开发同事帮忙开通。
  4. 记录对错，改说明，再试一遍。答错的看原因：缺资料，缺数据，还是说明没写清楚。通常两三轮就能看出这个场景行不行。
  5. 把结果写进方案。工作说明、需要接的系统清单、测试问题，正好对应方案的第 3、6、8 项。

附：给开发同事的示例代码

示例用 Google 的 Gemini 模型，通过 Vertex AI 用服务账号鉴权，其他模型的接法大同小异。服务账号的 JSON 凭证由管理员发放，放在代码仓库以外，路径写进环境变量，不要提交到 Git。下面三段代码在我们的环境里实际跑过。

1. 建立连接，问第一个问题

# pip install google-genai
import os
from google import genai
from google.genai import types
from google.oauth2 import service_account

creds = service_account.Credentials.from_service_account_file(
    os.environ["GOOGLE_CREDENTIALS_FILE"],
    scopes=["https://www.googleapis.com/auth/cloud-platform"],
)
client = genai.Client(
    vertexai=True,                                  # 走 Vertex AI，用服务账号鉴权
    project=os.environ["GOOGLE_CLOUD_PROJECT"],
    location="global",
    credentials=creds,
)
MODEL = os.environ["GEMINI_MODEL"]                  # 填项目里已开通的模型

reply = client.models.generate_content(
    model=MODEL,
    contents="海运从广州到雅加达一般要多久？",
    config=types.GenerateContentConfig(system_instruction="你是物流客服助手，回答不超过两句。"),
)
print(reply.text)

多运行几次，回答的天数可能都不一样。它用的是通用常识，不是公司的时效规则。

2. 提取开单信息，输出固定格式

from typing import Optional
from pydantic import BaseModel, Field

class Order(BaseModel):
    receiver_name: Optional[str] = Field(description="收件人姓名")
    phone: Optional[str] = Field(description="电话")
    city: Optional[str] = Field(description="城市")
    goods: Optional[str] = Field(description="货物和数量")
    uncertain_fields: list[str] = Field(description="消息里没有或拿不准的字段")

reply = client.models.generate_content(
    model=MODEL,
    contents="Halo kak, kirim ke Budi 0812-3456-7890, Surabaya, 20 箱手机壳",
    config=types.GenerateContentConfig(
        system_instruction="从客户消息中提取开单信息。推不出的字段填 null，并写进 uncertain_fields。",
        response_mime_type="application/json",
        response_schema=Order,
    ),
)
order = reply.parsed          # 已经是 Order 对象，格式不对会报错
print(order)

3. 工具调用：让它自己查运单

def query_waybill(waybill_no: str) -> dict:
    """按运单号查询物流轨迹和当前状态。"""
    return {"location": "GW 中转站", "last_update": "48 小时前", "status": "无新轨迹"}  # 换成调用运单系统

def query_exception(waybill_no: str) -> dict:
    """按运单号查询异常记录和处理进度，轨迹长时间没有更新时调用。"""
    return {"node": "GW 中转站", "exception": "分拣异常，面单破损", "progress": "待现场补打面单"}  # 换成调用异常系统

chat = client.chats.create(
    model=MODEL,
    config=types.GenerateContentConfig(
        system_instruction="你是物流查询助手。先用工具查真实数据，再给一句话结论和下一步建议。只用工具返回的信息。",
        tools=[query_waybill, query_exception],       # 直接传 Python 函数，SDK 负责执行并把结果交回模型
    ),
)
print(chat.send_message("运单 SG123456 怎么还没到？").text)

我们实际运行时，模型先查了轨迹，看到 48 小时没有新轨迹，又自己决定去查异常记录，最后回答：在 GW 中转站分拣异常，面单破损，已 48 小时无新轨迹，正在等现场补打面单。这就是第五节那个循环最简单的形式。函数的说明文字是模型选择工具的依据，写得越清楚，它选得越准。

这两个函数只查询、不改数据，所以可以交给 SDK 自动执行。会改变业务状态的操作不要这样接：让模型提出要做什么，由程序展示给用户，用户确认后再执行，并记录日志。

最后

回到开头那个答错的例子。换一个更强的模型，它多半还是会答错，因为它仍然看不到这票货的数据。把查询接上，把规则整理好，写清楚什么时候交给人，同一个模型就能答对。

AI 不是许愿池，扔进去资料，不会自动掉出答案。它更像一个能力很强的新同事：交代清楚，给对工具，定好边界，它就能实实在在地分担工作。
